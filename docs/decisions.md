| D-002 | Root `docs/` + a README per sub-project | One home per topic, no drift | 🟢 | A README passes ~1 page |
| D-003 | Server in Rust + tokio | Learning goal; safe and fast async | 🟢 | — |
| D-004 | Shared Rust `core` crate for server, cli, desktop | Write the protocol once; the cli tests what the desktop runs | 🟡 | — |
| D-005 | ~~Android stays Kotlin~~ **Replaced by D-016** | The existing app is Flutter | — | — |
| D-006 | ~~Protobuf payload~~ **Replaced by D-017** | — | — | — |
| D-007 | Content-addressed chunks, SHA-256, fixed 1 MiB | Dedupe, integrity, resume; SHA-256 is in Rust (sha2) and Dart (crypto) | 🟡 | CDC trigger in roadmap |
| D-008 | Upload = FileOffer → NeedChunks → ChunkData → Commit | Resume and dedupe for free; same idea as Syncthing / Immich | 🟢 | — |
| D-009 | SQLite catalog, written by one task only | Simple, crash-safe, no write races | 🟢 | — |
| D-010 | ~~Phone makes its own cert~~ **Replaced by D-018** | — | — | — |
| D-011 | No port open to the internet; remote access only via WireGuard | Smallest attack surface | 🟢 | — |
| D-012 | LAN discovery via mDNS | LocalSend model; no IP typing | 🟡 | — |
| D-013 | Disks: ZFS mirror (borrowed, not built) | Mistakes in disk code lose data | 🟡 | Hardware known |
| D-014 | Desktop app after M6 (M7) | Not needed for phone backup | 🟢 | — |
| D-015 | No dependency on MinIO or filebrowser | Both archived in 2026 | 🟢 | — |
| D-016 | Phone app = new Flutter app in `mobile/`, copying Protocol Lab's patterns (codec pure, Link = I/O, decoders never throw) | Protocol Lab is Flutter; it stays its own repo (it also holds ESP32 firmware and 25 unrelated tools) | 🟢 | — |
| D-017 | Hand-written binary payloads; `protocol/spec.md` + golden vectors that Rust and Dart both pass (generated by a third encoder in Python) | See every byte (Protocol Lab rule); no protoc toolchain; vectors prove both sides agree | 🟢 | — |
| D-018 | Server is a mini CA: self-signed server leaf (pinned by clients) + separate device CA that issues each device's cert + key in PairOk; clients connect by IP with no hostname check | No X.509 building on the phone; IPs change | 🟡 | QR / PAKE pairing (Later) |
| D-019 | Pull-based download: ReadFile, then ReadChunk per chunk; ListDevices so a new phone can restore an old phone's files | One reply per request; client controls resume | 🟢 | — |
| D-020 | No reference counts; unused chunk = no `version_chunks` / `upload_chunks` row, deleted inside the writer after 24 h | Fewer bookkeeping bugs, no cleanup/upload race | 🟢 | — |
| D-021 | Develop and test on this Linux PC; NAS-only steps stay ⚪ until hardware exists | Hardware not chosen (O-3) | 🟢 | O-3 answered |
| D-022 | Device cert + key stored as app-private files, not secure storage | dart:io TLS needs raw key bytes; avoids a plugin in the background job | 🟡 | — |
| D-023 | Admin Unix socket `<data_dir>/admin.sock` for pair, devices, scrub-now | A background service can't print a pairing code otherwise; tests use it | 🟢 | — |
| D-024 | Config file at `/etc/haotrannas/config.toml`; default `pairing_networks` = 192.168.0.0/16 + 172.16.0.0/12 (no 10.0.0.0/8: it contains the WireGuard subnet); config rejects any overlap with 10.66.0.0/24 | Config is not data; pairing must stay LAN-only | 🟢 | — |
| D-027 | Commit re-hashes every chunk on disk, not only the whole file: a chunk damaged on disk is marked bad and the client gets CHUNKS_MISSING (re-offer heals it), not FILE_HASH_MISMATCH | Bit rot between offer and commit must not throw away a good upload | 🟢 | — |
| D-028 | Loopback (127.0.0.0/8, ::1) may always pair, besides `pairing_networks` | Local access to the NAS already means full control; tests pair on localhost | 🟢 | — |
| D-029 | Commit of an upload identical to the latest version (same size, time, hash, all chunks ok) returns that version instead of adding a duplicate | Closes the lost-CommitOk race found in wave 3 | 🟢 | — |
| D-026 | Dev mode (`--dev-plain`, loopback only) uses a real `devices` row id 1 named `dev` with an all-zero cert hash; dev mode refuses a data folder that has real devices; TLS mode will refuse to start while the dev row exists | Uploads in M1/M2 need a real device row; no certificate hashes to all zeros, so no TLS client can ever match it | 🟢 | Wave 4 (TLS run) |
| D-030 | Clients wait for `CommitOk` in proportion to the file size: 30 s + 1 s per 20 MiB (spec §8, §14); every other request keeps its fixed timeout | The server re-hashes the whole file before CommitOk; a fixed 10–30 s timeout made every big file fail on a slow disk (found when e2e tests ran on the slow `/mnt/storage` disk) | 🟢 | Real NAS disk speed measured |
| D-031 | `ListDevices` lists revoked devices too (no wire change; DeviceEntry has no revoked flag) | A lost phone is revoked, and the new phone must still find it to restore its files (D-019, D-025) | 🟢 | The app needs to label revoked devices → add a flag in protocol v2 |
| D-032 | Phone backup runs newest first (since D-038: per album, Camera first), with a time budget; a stopped run resumes by re-offering (the server keeps uploaded chunks) | New photos are safe first; WorkManager stops jobs after ~10 min | 🟢 | Users want "oldest first" for a first full backup |
| D-033 | Phone keeps backup state, settings, last reports and a run lock in one SQLite file (no shared_preferences) | One atomic store that the app and the background job both open | 🟢 | Lock problems seen on a real phone |
| D-034 | "Back up now" runs on any network; Wi-Fi only / charging only shape only the background job | A tap is an explicit request | 🟡 | Hao wants the tap to respect the settings |
| D-035 | Scrub and cleanup run only inside the running server (admin `scrub-now`, `scrub-report`, `cleanup-now`); no offline mode | One catalog writer (D-020); an offline scrub would race a running server | 🟢 | Need to check a data folder while the server is stopped |
| D-036 | Scrub is rate-limited (64 MiB/s, a constant); orphan chunk files (crash between row delete and file delete) are removed by a once-a-day pass after the 24 h grace | Uploads must not starve; walking every chunk file hourly is waste | 🟢 | Scrub too slow or too heavy on the real NAS disk |
| D-037 | Phone backs up chosen albums only; never chosen = the `Camera` album; the choice is saved with the settings (`folder_ids`) | First phone test: a whole library is too big to start with; Immich and Ente ask for albums too | 🟢 | Phones without a `Camera` album, or users who want "everything" by default |
| D-038 | "Back up now" is a one-off long-running workmanager job (dataSync foreground service, fixed notification, up to 5 h); the app sees it through workmanager progress, stops it through a `stop_requested` value; the job refreshes the run lock every minute. Every run uploads while it scans (no full scan first) | First phone test: a big library spent the whole 15 min budget scanning and nothing was uploaded, with no numbers on screen | 🟡 | Android 15 dataSync time limit hit, or live numbers wanted in the notification |
| D-040 | Client logic shared by the phone and PC apps lives in one Flutter package, `dart_client/` (`haotrannas_client`): protocol codec, Link/TLS, discovery, pairing, upload/download, backup runner/store/controller and the `MediaSource` interface. Apps keep only their platform parts (phone: photo_manager source, workmanager jobs, multicast lock; PC: folder source) and their UI. The SQLite store takes a `DatabaseFactory` (phone: sqflite plugin, PC: ffi) | Conventions forbid anything → mobile; copying 8k tested lines into the PC app would make two clients drift | 🟢 | A third Dart app, or the package grows UI code |
| D-039 | PC app = Flutter desktop, Linux first (`desktop/`). Scope: back up chosen PC folders, browse and restore (a file or a whole folder, never replacing a PC file), NAS admin (devices, revoke, pairing code, scrub, cleanup). No server-config editing, no delete. Backup runs while the app is open: hourly timer, 6 h budget (no service, no tray yet). Remote path = `<folder name>/<path inside>`; two chosen folders may not share a name. The run lock is named `desktop-<pid>` and a dead app's lock is freed at start | Same UI stack as the phone; a GUI that edits config or deletes is risk on the box holding every backup (conventions §4) | 🟢 | Windows wanted, backups needed with the app closed, or a tray |
| D-041 | PC admin = the existing admin.sock line protocol (D-023), directly when the server runs on this PC, else through `ssh -N -L <local sock>:<data_dir>/admin.sock` with the user's keys (BatchMode, no password stored). No admin over TLS, no web admin, no new port | No new server code or attack surface; SSH already guards the NAS | 🟡 | ⚪ The NAS SSH user cannot open admin.sock (0600, user haotrannas): a group for it is due in M3n |
| D-042 | Phone restore puts a photo or video into the gallery (MediaStore through photo_manager, album `Pictures/HaoTranNAS`, dated with the file's own time) and deletes the app's copy; other files stay in the app's folder and the screen says so. The gallery step lives in `mobile/`, so `restoreToPhone` (dart_client) only downloads. The Backup tab leads with one headline built from the last run (Backed up / N files still to back up / Last backup did not finish / Not backed up yet), with no extra library scan: the run summary keeps `files_left` (found but not reached; a lower bound when the scan stopped early). Settings keep the chosen album names next to the ids (`folder_names`, display only) so the Backup tab names them without asking for photo access | First UI review: a restore ended as a path the user cannot open; the home screen never said whether the photos are safe | 🟡 | ⚪ Android 9 and older (needs WRITE_EXTERNAL_STORAGE at run time); an exact "waiting" count wanted (needs a scan) |
| D-043 | iPhone app = the same Flutter app (`mobile/ios/`), no fork. No Mac and no paid Apple account: CI builds an unsigned IPA, Hao sideloads it with a free Apple ID (SideStore / AltServer, re-sign every 7 days). Find the NAS with the phone's Bonjour (package:bonsoir, `NSBonjourServices`), not our raw multicast socket. No background job: automatic backup = a run each time the app opens or comes to the front; Wi-Fi/charging switches hidden. iPhone photos go to `iPhone/<yyyy>-<mm>/<name>` (UTC month of the photo); restored ones go to Photos (Recents) | iOS sends multicast only with Apple's multicast entitlement (paid, by request); iOS has no long-running background work and our TLS protocol cannot ride a background URLSession; iOS photos have no folder and `IMG_xxxx` names roll over | 🟡 | A paid account or a Mac (then TestFlight / BGProcessingTask overnight); iPhone checks fail; Immich-style background upload wanted |
| D-044 | A second NAS host built with Yocto in `yocto/` (M9): kas file + one layer `meta-haotrannas` (distro `haotrannas`, image `haotrannas-image`), same shape as Bootlin yocto-kiss. Board support is borrowed from `meta-raspberrypi`. The build PC's settings live in `yocto/build-config/this-pc.yaml`; its no-password root login is for bench tests only, never in a shipped image | Learning goal (Yocto); a small image that lists only what the NAS runs, rebuilt the same way from text in git | 🟡 | M9 done: pick which host (M3n or M9) becomes the real NAS |
| D-045 | The Yocto image targets the Raspberry Pi 5 (MACHINE `raspberrypi5`, ARM64). O-3's mini PC stays the M3n host | Cheaper, low power, good board support layer; the Rust server must then build for ARM64 too | 🟡 | Pi 5 too slow for hashing at backup speed, or disk bays needed |
| D-046 | Disks on the Yocto image: mdadm RAID1 (in openembedded-core), not ZFS. D-013 (ZFS) stays for the M3n host | ZFS is not in mainline Linux: on Yocto it needs an extra layer and a kernel module that must match the kernel. Bit rot is still repaired by "verify backup" (M6) | 🟡 | A checked ZFS layer for the Yocto release exists and the repair-by-verify path proves too slow |
| D-047 | Android app asks once to be exempt from the battery saver (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, the system dialog) when automatic backup is turned on; Settings shows the state with an Allow tile | Samsung, Xiaomi and others stop workmanager jobs under battery optimization, so "new photo backed up without a tap" (M4) fails silently. Google Play limits this permission, but the app is sideloaded from CI | 🟡 | The app goes to Google Play, or the background job proves reliable without it |
| D-025 | Revoking a device never deletes its backups: `devices.revoked_at_ms` marks it, a revoked cert is refused like an unknown one; `remove_device` stays only for devices with no backups | A lost phone must be locked out while its photos stay restorable | 🟢 | — |
