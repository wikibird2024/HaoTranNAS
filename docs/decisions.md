| D-010 | ~~Phone makes its own cert~~ **Replaced by D-018** | — | — | — |
| D-011 | No port open to the internet; remote access only via WireGuard | Smallest attack surface | 🟢 | — |
| D-012 | LAN discovery via mDNS | LocalSend model; no IP typing | 🟡 | — |
| D-013 | Disks: ZFS mirror (borrowed, not built) | Mistakes in disk code lose data | 🟡 | Hardware known |
| D-014 | Desktop app after M6 (M7) | Not needed for phone backup | 🟢 | — |
| D-015 | No dependency on MinIO or filebrowser | Both archived in 2026 | 🟢 | — |
| D-016 | Phone app = new Flutter app in `mobile/`, copying Protocol Lab's patterns (codec pure, Link = I/O, decoders never throw) | Protocol Lab is Flutter; it stays its own repo (it also holds ESP32 firmware and 25 unrelated tools) | 🟢 | — |
| D-017 | Hand-written binary payloads; `protocol/spec.md` + golden vectors that Rust and Dart both pass (generated by a third encoder in Python) | See every byte (Protocol Lab rule); no protoc toolchain; vectors prove both sides agree | 🟢 | — |
| D-018 | Server is a mini CA: self-signed server leaf (pinned by clients) + separate device CA that issues each device's cert + key in PairOk; clients connect by IP with no hostname check | No X.509 building on the phone; IPs change | 🟡 | QR / PAKE pairing (Later) |
| D-019 | Pull-based download: ReadFile, then ReadChunk per chunk; ListDevices so a new phone can restore an old phone's files | One reply per request; client controls resume | 🟢 | — |
| D-020 | No reference counts; unused chunk = no `version_chunks` / `upload_chunks` row, deleted inside the writer after 24 h | Fewer bookkeeping bugs, no cleanup/upload race | 🟢 | — |
| D-021 | Develop and test on this Linux PC; NAS-only steps stay ⚪ until hardware exists | Hardware not chosen (O-3) | 🟢 | O-3 answered |
| D-022 | Device cert + key stored as app-private files, not secure storage | dart:io TLS needs raw key bytes; avoids a plugin in the background job | 🟡 | — |
| D-023 | Admin Unix socket `<data_dir>/admin.sock` for pair, devices, scrub-now | A background service can't print a pairing code otherwise; tests use it | 🟢 | — |
| D-024 | Config file at `/etc/haotrannas/config.toml`; default `pairing_networks` = 192.168.0.0/16 + 172.16.0.0/12 (no 10.0.0.0/8: it contains the WireGuard subnet); config rejects any overlap with 10.66.0.0/24 | Config is not data; pairing must stay LAN-only | 🟢 | — |
| D-027 | Commit re-hashes every chunk on disk, not only the whole file: a chunk damaged on disk is marked bad and the client gets CHUNKS_MISSING (re-offer heals it), not FILE_HASH_MISMATCH | Bit rot between offer and commit must not throw away a good upload | 🟢 | — |
| D-028 | Loopback (127.0.0.0/8, ::1) may always pair, besides `pairing_networks` | Local access to the NAS already means full control; tests pair on localhost | 🟢 | — |
| D-029 | Commit of an upload identical to the latest version (same size, time, hash, all chunks ok) returns that version instead of adding a duplicate | Closes the lost-CommitOk race found in wave 3 | 🟢 | — |
| D-026 | Dev mode (`--dev-plain`, loopback only) uses a real `devices` row id 1 named `dev` with an all-zero cert hash; dev mode refuses a data folder that has real devices; TLS mode will refuse to start while the dev row exists | Uploads in M1/M2 need a real device row; no certificate hashes to all zeros, so no TLS client can ever match it | 🟢 | Wave 4 (TLS run) |
| D-030 | Clients wait for `CommitOk` in proportion to the file size: 30 s + 1 s per 20 MiB (spec §8, §14); every other request keeps its fixed timeout | The server re-hashes the whole file before CommitOk; a fixed 10–30 s timeout made every big file fail on a slow disk (found when e2e tests ran on the slow `/mnt/storage` disk) | 🟢 | Real NAS disk speed measured |
| D-031 | `ListDevices` lists revoked devices too (no wire change; DeviceEntry has no revoked flag) | A lost phone is revoked, and the new phone must still find it to restore its files (D-019, D-025) | 🟢 | The app needs to label revoked devices → add a flag in protocol v2 |
| D-032 | Phone backup runs newest first, with a time budget; a stopped run resumes by re-offering (the server keeps uploaded chunks) | New photos are safe first; WorkManager stops jobs after ~10 min | 🟢 | Users want "oldest first" for a first full backup |
| D-033 | Phone keeps backup state, settings, last reports and a run lock in one SQLite file (no shared_preferences) | One atomic store that the app and the background job both open | 🟢 | Lock problems seen on a real phone |
| D-034 | "Back up now" runs on any network; Wi-Fi only / charging only shape only the background job | A tap is an explicit request | 🟡 | Hao wants the tap to respect the settings |
| D-035 | Scrub and cleanup run only inside the running server (admin `scrub-now`, `scrub-report`, `cleanup-now`); no offline mode | One catalog writer (D-020); an offline scrub would race a running server | 🟢 | Need to check a data folder while the server is stopped |
| D-036 | Scrub is rate-limited (64 MiB/s, a constant); orphan chunk files (crash between row delete and file delete) are removed by a once-a-day pass after the 24 h grace | Uploads must not starve; walking every chunk file hourly is waste | 🟢 | Scrub too slow or too heavy on the real NAS disk |
| D-025 | Revoking a device never deletes its backups: `devices.revoked_at_ms` marks it, a revoked cert is refused like an unknown one; `remove_device` stays only for devices with no backups | A lost phone must be locked out while its photos stay restorable | 🟢 | — |
